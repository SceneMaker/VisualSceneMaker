# Pattern 1.1: Fixed sequence

**Level:** 1 (Sequences) · **Catalogue id:** `sequence` · **Status:** template and detector implemented
**Date:** 2026-08-13
**Parent concept:** [`../sceneflow-modelling-support-concept.md`](../sceneflow-modelling-support-concept.md) §3

Wording currently under expert review:

> The agent works through a series of steps in a fixed order. Each step begins only once the
> previous one has finished.
>
> *In practice:* The agent greets the visitor, then explains what the session will be about, then
> asks the first question, always in that order.

This document specifies what that promise costs to keep.

---

## 1. What the author means

"First this, then that." The author thinks in steps, each step being something the agent does that
takes time, and expects step two to start when step one is over. Nothing about the author's mental
model mentions nodes, edges, or blocking.

The pattern is the foundation of Level 1: patterns 1.4, 1.6 and 1.8 are all sequences with extra
structure, and the applied `doc/IntakeInterview` project is essentially one long instance of it.

---

## 2. Runtime semantics: what "then" actually means

This is the load-bearing section. The author's promise holds automatically in one case and must be
built by hand in another, and the difference is invisible on the canvas.

### 2.1 A scene step blocks. "Then" is free.

Playing a scene parks the interpreter thread until the scene has finished. The chain is:

| Stage | Evidence |
|---|---|
| Evaluator releases the interpreter lock around the call, which is only necessary for a call expected to block | `core/.../interpreter/Evaluator.java:162-181` |
| `ReactivePlayer` starts a worker and joins it in a retry loop | `core/.../player/ReactivePlayer.java:412-433` |
| Each utterance is scheduled as a `SpeechActivity`, hard-wired blocking | `core/.../activity/SpeechActivity.java:41` (`super(Type.blocking, ...)`) |
| The scheduler joins any activity whose type is blocking | `core/.../activity/scheduler/ActivityScheduler.java:111-128` |
| A character plugin waits for real speech completion, bounded by a 20 s timeout | `plugins/charamel-embed/.../CharamelEmbedExecutor.java:649-705` |

The decisive field evidence is `plugins/charamel-ws/ExampleProject/sceneflow.xml`, where node N1
plays scene `welcome`, a bare EEdge leads to N5 which plays scene `name`, and a bare EEdge leads
back to N1. If scene playback did not block, that two-node cycle would spawn playback as fast as the
interpreter can cycle. It is a shipped demo, so it does not. `doc/IntakeInterview/sceneflow.xml:82-131`
relies on the same thing: `Greet` hands straight to `AskName` on a bare EEdge, and the two scenes do
not talk over each other.

There is no non-blocking scene option. `PlayScenesActivity` has no mode field, and the grammar's
`UnblockSceneGroup` and `UnblockSceneScript` commands both throw `InterpreterError` in the Evaluator
(`Evaluator.java:184-187`), so they are dead syntax an author or a generator must never emit.

### 2.2 An action step blocks only until `execute()` returns.

A `PlayAction` node command defaults to blocking (`ReactivePlayer.java:158-163` overrides
`ActionActivity`'s own parallel default), but the join ends the instant the plugin's `execute()`
method returns. It does not wait for whatever that method started.

So `[timer init id=one]` "blocks" for microseconds: `TimerExecutor.init()` is a single map insert.
A plugin that plays a two-second gesture and returns immediately gives the author overlapping steps
with no warning. Conversely a plugin that does its work inside `execute()`, as Charamel's
`sleepForBlockingEnvelope` does, gives correct sequencing from the same bare edge.

**Consequence for the pattern:**

| Step kind | Does "then" hold with a bare EEdge? |
|---|---|
| Play a scene | Yes, always |
| Set a variable | Yes, trivially |
| Plugin action, work done inside `execute()` | Yes |
| Plugin action, fire and forget (timer, HTTP post, "start moving") | **No.** Step two overlaps step one |

The last row is the only case where the pattern needs more than a chain, and it is not detectable
from the flow. It depends on the plugin's implementation.

### 2.3 Three traps that follow from the execution order

The step routine is strictly: enter node, run every command to completion, then look for an
outgoing edge (`core/.../interpreter/Process.java:550-742`). The only yield between commands is an
IEdge check. From that:

1. **A timeout edge does not overlap a blocking command.** Timers start only after the command
   phase ends (`Process.java:613-619`, whose own comment calls it "the node's blocking command
   phase"). A node that plays a five second scene and carries a 1000 ms TEdge continues after six
   seconds, not one. This matters when 1.1 composes with 1.2 (Timed pause): the pause is added
   after the step, which is what an author expects, but for the opposite reason than they assume.
2. **A condition edge cannot observe anything during a step.** CEdges are evaluated only after the
   command phase (`:587-604` before `:635`). Reacting to something that happens *while* a step runs
   requires an IEdge, which aborts the step. This is the boundary between 1.1 and 3.1.
3. **The blocking default is inverted between the two authoring surfaces.** An inline SceneScript
   action is fire-and-forget unless marked `blocking='true'` (`core/.../ActionBlockingUtil.java`),
   while a SceneFlow `PlayAction` node command is blocking unless marked Concurrent. Same author,
   two windows, opposite defaults.

### 2.4 One default edge per node

`EEdge` and `TEdge` share a single slot on a node (`BasicNode.mDEdge`), and the compiler throws if a
second one is attached (`SceneFlowIrPatchApplier.java:435-442`). A sequence step therefore cannot
carry both an EEdge to the next step and a TEdge for anything else. A chain is fine, since each step
has exactly one outgoing EEdge, but any variant that wants a per-step timeout has to spend that slot
on the TEdge instead and cannot also have an EEdge.

## 3. Variants

**A. Bare chain (default).** One node per step, each with its commands, joined by EEdges. Correct
whenever every step blocks. This is what the assistant should generate unless it has reason to think
otherwise.

**B. Chain with a completion handshake.** For a fire-and-forget step: the plugin writes a variable
on completion via `mProject.setVariable(...)`, and a wait node sits between the two steps, either as
a TEdge self-loop plus a CEdge on that variable (the IntakeInterview shape, reaction lags by up to
the interval) or as an IEdge on an Event variable (no polling, immediate, and able to preempt). This
requires the plugin to report completion at all. If it does not, the only remaining option is a
TEdge with a guessed duration, which is what `doc/DesignPatterns` N41/N42 amounts to.

**C. Chain with deliberate pauses.** Variant A plus 1.2 on the connecting edges, spending the
default-edge slot on TEdges instead of EEdges.

## 4. What a step needs to exist

A scene step has a four-link dependency chain, and breaking any link makes the step silently do
nothing:

```
scene name in SceneScript
  → its speaker (e.g. Xenia)
    → an Agent binding in project.xml (Agent name="Xenia" device="CharamelEmbedXenia")
      → a loaded Plugin providing that device
```

Verified against `plugins/charamel-embed/ExampleProject`, where scene `welcome` has
`speaker="Xenia"`, matched by `Agent name="Xenia" device="CharamelEmbedXenia"`, matched by a
`Plugin` entry with `load="true"`.

**The snapshot now carries the inventory needed to check this** (added 2026-08-13, snapshot version
`1.1`). A top-level `script` section lists each scene group with its language variants, speakers,
turn and word counts, parameters, referenced agents and inline command names:

```json
{ "name": "welcome", "languages": ["de"], "speakers": ["Xenia"],
  "turnCount": 1, "wordCount": 9, "parameters": [],
  "referencedAgents": ["time"],
  "inlineCommands": ["background", "emotion", "init", "nod", "pause", "time"] }
```

That is enough to check every link of the chain: the scene exists, its speaker is a declared agent,
that agent's device is a loaded plugin, and the commands the scene uses inline are provided by
plugins the project actually has. `doc/DesignPatterns` supplies a ready-made negative case, since
its scene `Welcome` is spoken by `Anne` while the project declares only the `timer` agent.

Two further requirements the inventory revealed:

- **A scene can take parameters.** `show_summary` in `doc/IntakeInterview` consists of a single
  `SceneParam`, so `PlayScene("show_summary")` without an argument would play nothing useful. The
  assistant must pass a value or bind a variable, and the IR's `PlayScene` argument list is the
  place for it.
- **A scene may address agents other than its speaker.** `machwas` in the charamel-embed example
  is spoken by `Xenia` but carries a command addressed to `Bob`, so the resource check has to walk
  `referencedAgents` too, not just `speakers`.

Five validator rules consume the inventory (added 2026-08-13):

| Rule | Severity | Catches |
|---|---|---|
| `SCENE_REF_UNKNOWN` | warning | A literal scene name the project does not declare |
| `SCENE_PARAM_MISSING` | warning | A declared parameter the call does not supply |
| `SCENE_PARAM_UNKNOWN` | warning | A supplied field the scene does not declare, usually a typo |
| `SCENE_ARG_NOT_STRUCT` | warning | An argument that is not a struct, so binds nothing |
| `COMMAND_TEXT_INVALID_QUOTE` | error | The single-quote corruption from §6 |

The scene rules are warnings, matching `VAR_REF_UNKNOWN`, because a scene and its parameters are
content the author may still be editing. The quote rule is an error because no bare single quote is
ever correct. Severities are configured in `meta-to-sceneflow-mapping.json`, so promoting one is a
one-line change.

Three structural rules complete the set:

| Rule | Severity | Catches |
|---|---|---|
| `EDGE_DEFAULT_DUPLICATE` | error | A node that would end up with two default edges, per §2.4 |
| `NODE_UNREACHABLE` | warning | A created node that is neither a start node nor any edge's target |
| `NODE_DEAD_END` | warning | Execution stopping at a created node with no outgoing edge |

`NODE_DEAD_END` deserves a note, because every generated sequence triggers it exactly once, on the
final step. That is deliberate rather than noise: it is the prompt for the elicitation question in §5
item 5, which is what should follow the last step. The message says execution ends there rather than
implying a defect.

`EDGE_DEFAULT_DUPLICATE` counts edges already in the flow as well as those the patch creates, but
only when the patch deletes no edges. A `delete_edge` names an edge id and snapshot edges carry none,
so a patch that removes an edge cannot be reconciled with the existing flow, and reporting a conflict
the deletion resolves would be worse than missing one.

**Arguments bind by name, not by position.** `ReactivePlayer.getSubstitutions`
(`core/.../player/ReactivePlayer.java:440-457`) reads only `StructValue` arguments and silently
ignores everything else, so this is not an arity check in the usual sense:

```
PlayScene("Address", { user = username })   // correct
PlayScene("Address")                        // SCENE_PARAM_MISSING
PlayScene("Address", { usr = username })    // SCENE_PARAM_UNKNOWN and SCENE_PARAM_MISSING
PlayScene("Address", username)              // SCENE_ARG_NOT_STRUCT: looks like it passes a value, supplies nothing
```

The struct's concrete syntax is braces, `{ name = value }`. Verified by round-trip: that command text
compiles to the same XML as the hand-authored `PlayScene` in
`/Users/gebhard/Code/Temp/ScenesActionsCommands`.

These checks parse the command with `GlueParser` and inspect the AST rather than matching text. That
replaced an earlier regex and is what makes the dynamic forms below fall out correctly: a name that
is not a `StringLiteral` simply yields nothing to check.

**A scene name is not always a literal, and the rule must not pretend otherwise.**
`/Users/gebhard/Code/Temp/ScenesActionsCommands` shows the legitimate dynamic forms:

```
PlayScene(topic)                          // name held in a variable
PlayScene("Topic_" + topic)               // name built at runtime
PlayScene("Address", [user = user_name])  // literal name, played with arguments
```

Only the third is checkable. The first two are left alone, because the name is unknowable until
runtime and reporting them would train authors to ignore the rule. The argument form is still
checked on its first argument.

*Correction to an earlier claim in this document:* I had written that a scene rule would also catch
the single-quote defect, on the reasoning that a mis-lexed name becomes an unknown variable
reference. That was wrong twice over. `VAR_REF_UNKNOWN` only inspects edge conditions, not command
text, and since a variable is a legitimate scene name a scene rule cannot flag one either. Verified
empirically: before the quote rule existed, `PlayScene('Welcome')` passed validation with no issue
at all, even against a snapshot that declares `Welcome`. Hence the separate rule.

## 5. What the assistant must elicit

1. **The steps, in order.** Natural language usually carries them ("first ... then ... finally"), so
   the resolver needs a step splitter. Fall back to asking for them one at a time.
2. **Per step, what kind:** say something (a scene), do something (a plugin action), or remember
   something (a variable assignment).
3. **Per scene step, the wording.** Either the author writes it now, or the assistant creates a
   named empty scene as a stub for later. Creating stubs is the better default, since it keeps the
   flow shape reviewable before the wording exists.
4. **Whether any step is fire-and-forget.** The assistant can determine this from
   `plugin-properties.json` rather than asking, if the spec is extended to declare per-command
   completion behaviour. Today it cannot be known, which argues for adding a
   `completes: immediate | on-finish | unknown` field to declared commands.
5. **Where the sequence attaches** and **what follows the last step.** A generated final step with
   no outgoing edge is a dead end that no validator rejects. The author must choose a continuation
   or accept a deliberate stop.

## 6. Generated IR

Verified example: [`../sceneflow-ir.sequence.example.json`](../sceneflow-ir.sequence.example.json)
(three steps, root level). It passes `./gradlew validateSceneFlowIr` and compiles with
`./gradlew compileSceneFlowIr` to a chain matching hand-authored IntakeInterview structure.

Shape per step: `create_node` (first with `isStartNode: true`, which correctly appends to the root's
`start` attribute), `add_node_command`, and `create_edge` with `edgeType: "EEDGE"` between
consecutive steps.

The template produces exactly this shape. Generating from "First greet the visitor, then ask name,
then show summary." against `doc/IntakeInterview` resolves all three steps to scenes that already
exist and compiles into the project:

```
GreetVisitor   plays greet          -> AskName2
AskName2       plays ask_name       -> ShowSummary2
ShowSummary2   plays show_summary   -> END
```

Node ids are deduplicated against the project's existing node ids and names, which is why the
second and third steps carry a suffix here: IntakeInterview already displays nodes called `AskName`
and `ShowSummary`. Validation of that output reports one warning, `SCENE_PARAM_MISSING`, because
`show_summary` declares a `summary` parameter the generated call does not supply. That is the
correct outcome rather than a defect in the template: the value has to come from the author, and it
is exactly the question the assistant's elicitation phase should ask.

**The command text must use double quotes.** `PlayScene('greet')` is not a syntax error that stops
anything: the lexer prints `Illegal character: '''` to stdout, the parser then reads a bare
identifier, and the result compiles successfully into

```xml
<PlayScene><SimpleVariable name="greet"/></PlayScene>
```

which is a reference to a nonexistent *variable*, not the scene. Semantic validation passes and the
compiler reports OK. `PlayScene("greet")` produces the correct
`<StringLiteral><![CDATA[greet]]></StringLiteral>`. Nothing reported this at all until
`COMMAND_TEXT_INVALID_QUOTE` was added (see §4), which matters because any LLM-generated IR is
likely to reach for single quotes.

**Emit positions from the template.** The compiler has no fallback layout: `applyPosition` returns
early when position is absent (`SceneFlowIrPatchApplier.java:422-433`), leaving `graphics` null so
nodes collapse on the canvas. The pipeline's `assignCreateNodePositions`
(`SceneFlowSituationPipeline.java:820-867`) fills the gap only when the pipeline is the consumer,
and it ignores existing node coordinates, so its fixed `y: 340` row can land on top of the project's
existing nodes. It also wraps three per row inside a supernode, which would visually break a
sequence of four or more steps. A sequence template should emit `x = base + i·320` at constant `y`
itself.

## 7. Recognising a sequence, for preview and tutorial mode

Both the assistant's preview step and tutorial-mode verification depend on the detector layer in
`SceneFlowNarrativeExplainer`. It now recognises a chain as one thing (added 2026-08-13). Explaining
the generated flow returns a single finding phrased for an author rather than a scatter of edge
mechanics:

> A sequence of 3 steps runs in a fixed order: "GreetVisitor", then "AskName", then "ShowSummary".
> Each step begins once the previous one has finished, and the steps are joined by unconditional
> edges.

The generate-and-explain round trip is therefore symmetric: a situation becomes a chain, and the
chain reads back as the same sequence.

**Where a run stops** is the substance of the detector, because a chain that merely looks linear is
often something else:

- A step that carries any other outgoing edge, a guard, a fork, a probability or an interrupt, ends
  the run. What follows such a step is not simply "the next step". This is what separates a plain
  sequence from `doc/DesignPatterns` S4, whose middle step polls with a timeout and exits on a
  condition. S3, whose `Prepare` to `Execute` to `End` chain is pure, is correctly reported as a
  sequence; S4's near-identical chain is not.
- A target reachable from anywhere else ends the run, because it is a meeting point rather than the
  next step. In-degree is counted across the whole chart, supernode edges included.
- Self-loops and revisits end the run.

**Two nodes are not a sequence.** A run of three or more nodes becomes one `sequence` finding and its
hops are suppressed; a single hop stays `unconditional_transition`. One hop is a transition, and
naming it a sequence would both flood the inventory and tell an author nothing.

Verified on `doc/DesignPatterns` plus the generated chain: two sequences are found, and
`unconditional_transition` drops from 12 to 8, which is exactly the four hops the two sequences
subsume.

## 9. Corrections this raises elsewhere

- **Review sheet item 1.1 is accurate as written** for scene steps, which is what its example shows,
  and I recommend leaving it untouched while the review is in flight. Changing an instrument
  mid-study costs comparability, and the caveat is about realisation rather than about the concept
  the reviewer is being asked to judge.
- **Review sheet item 2.5** ("A secondary activity starts together with one step and finishes on its
  own. The conversation carries on regardless") describes behaviour that the default *does not*
  give: a `PlayAction` node command blocks unless it is Concurrent. When 2.5 is specified it must
  either require Concurrent mode or an FEdge branch. Flagged, not changed, for the same reason.
- **Both help files omit blocking entirely.** `sceneflow-help.html:411` says only that commands "run
  once when the node is entered", never how long the node stays. The closest statement is the
  i-edge versus c-edge note at `:347-353`, which presupposes that commands block without ever saying
  so. Given that this is the single fact an author needs in order to trust a sequence, it belongs in
  the help text.
- **`doc/DesignPatterns` cannot demonstrate this pattern.** Its sequence examples D3 and D4 have
  empty `<Commands>` and the project contains no `PlayScene` at all, so the gallery's sequence
  example cannot show that "then" means "after the previous step finishes". Adding one scene-playing
  chain there would make the point that the current example cannot.
